# Игровая логика и сохранения pre-MVP

Дата: 22.09.2026. Область: только HotelSimulation.cs, HotelSaveStore.cs, HotelSimulationTests.cs и этот отчёт. Контракт и HotelTypes.cs не изменены. Unity Editor/import не запускались, публикации нет.

## Реализовано

- Четыре номера 101–104, независимые occupancy/OOS, кровать 0/1/2, полотенца, мусор, протечка и вода. Начальная подготовка: 101 готов, 102 требует белья и мусора, 103 полотенца, 104 чистого белья.
- Два сотрудника с разнесёнными точками появления, эксклюзивное владение предметами, освобождение предмета/рабочей блокировки при disconnect. OwnerGuest багажа не меняется при переноске.
- Полный цикл queue → walking → staying → checkout → leaving → gone. Маршрут восстанавливается из стадии/координат, проходит коридор и дверь; обход стойки через x=1.85. Динамическое избегание игроков/тележки в scope не входит.
- Стойка: checkin(room), checkout(guest), compensate(guest). Заселение атомарно связывает номер и первого гостя очереди. Грязная/голая кровать, OOS, протечка и глубокая вода блокируют заселение; мелкий мусор и отсутствие полотенца допускаются с последствиями для впечатлений.
- Физический цикл dirty bed → dirtylinen → hamper, linen → bed, trash → trashbag → bin, towel → towel stand. Расходник используется один раз.
- Работа bed_N/trash_N/sink_N/water_N требует beginwork и heartbeat. Прогресс 0..1; timeout 0.8 с. Длительности: снять бельё 2 с, застелить 3 с, мусор 2 с, ремонт 5 с, швабра 3 с. Пауза без heartbeat, уход, потеря инструмента или disconnect отменяют действие. Одну цель обслуживает один сотрудник; разные цели можно обслуживать одновременно.
- Починка прекращает источник, но оставляет воду. Швабра убирает воду, но не чинит источник. В подготовке/итогах вода не растёт, работа доступна.
- Дополнительное полотенце — отдельный запрос, исходное полотенце остаётся на месте. Жалобы однократны по факту, относятся к действительно посещённому номеру. Компенсация улучшает впечатление, не чинит комнату. Отзывы строятся из воспоминаний, оплата/отзыв не повторяются.
- Длительность смены 480 с; 3 гостя в день 1, 4 далее; интервалы прибытия 85 с. Первый гость терпеливый. Запрос полотенца через 25 с проживания, протечка у одного гостя через 80 с, проживание 160 с. Ожидание регистрации ограничено 210 с; после 100 с ожидания оформления выезда происходит авторитетный автоматический расчёт.
- Фазы preparation/open/closing/summary. Хозяин id=0 подтверждает open/finish/nextday/upgrade/toggleRoom. Административные команды проверяют дистанцию до desk либо board. Клиенту доступны заселение/выезд/компенсация. Finish может досрочно закрыть смену; гости рассчитываются по текущим впечатлениям, грязь/вода/поломки сохраняются.
- Покупки один раз: toolbox 220 (второй физический инструмент), beds 400 (комфорт и +20 к тарифу), cart 320 (перевозка двух чемоданов). Оплата гостя: 80 + округление(satisfaction × 0.5) + бонус кровати; компенсация 25.
- Тележка: удерживая cart, pickup/interact чемодана загружает его; bag_N выгружает подходящий чемодан в номер. Груз хранит placedRoom=-1, holder=-1, ownerGuest остаётся прежним. После отпуска/загрузки тележка с грузом остаётся в мире. Позиции груза обновляются рядом с тележкой.
- Между днями запас пополняется до 12 белья и 12 полотенец с учётом ещё не использованных предметов в мире. Стоимость 4/2 за единицу плюс 30 содержания. Допускается долг для восстановления после плохого дня. Загрузка не запускает пополнение/покупку/расчёт повторно. Tasks() вычисляет русские задачи из мира.

## Команды для интегратора

- `beginwork`: bed_N, trash_N, sink_N, water_N. `interact` на этих же целях также начинает работу. `heartbeat` должен повторять активный target; 5 Гц достаточно.
- `interact`: linen, towels, hamper, bin, towel_N, bag_N; на ItemState.id эквивалентен pickup. Desk/board оставлены UI.
- `pickup`: ItemState.id. `drop`: ближайшая доступная позиция пола. Нельзя бросать предмет сквозь стену/наружу.
- `pose`: finite координаты внутри допустимой геометрии, yaw/pitch. Полная проверка скорости движения/коллизий игрока остаётся за контроллером/сетевым слоем; этот модуль не реализует соревновательный античит.
- `checkout` принимает только гостя, который физически дошёл до стойки. До этого возвращается русская причина.
- `HotelSaveStore.Load` возвращает null только при отсутствии основного файла и backup; повреждение обеих копий бросает InvalidDataException; более новая версия — NotSupportedException. Ошибки записи не выдаются за успех.

## Сохранения

Версия 1, envelope WorstHotelSave, SHA-256 payload, строгая проверка структуры/ссылок/типов/чисел/уникальности сущностей и постоянных инструментов. Запись immutable JSON-снимка во временный файл того же каталога с Flush(true), чтение/проверка записанных байтов, затем File.Replace с .bak или File.Move для нового слота. Нет небезопасного delete+move fallback. Ошибка/несовместимая файловая система оставляет старый checkpoint.

Повреждённый основной файл восстанавливается из .bak. Следующая запись после recovery сохраняет корректный backup, не заменяет его повреждённым файлом. Более новая версия не откатывается молча на старый backup и не перезаписывается. Другой worldId в занятом слоте требует отдельного пути.

При загрузке мир/время/гости/покупки сохраняются, игроки удаляются, held-объекты безопасно отпускаются на пол, рабочие lease не продолжаются, маршрут гостя строится из состояния. Время отсутствия не добавляется. Save/Execute/Tick вызывать последовательно на потоке хоста; статическая блокировка защищает только файловые операции, не делает mutable State потокобезопасным.

## Принятые ограничения и согласование

- DTO не содержал ID операции. В симуляции установлены state guards против повторных оплат, покупок, расходования/захвата предметов и переходов дня. Полный replay guard для toggleRoom и повторного checkin другого номера должен работать в транспортном слое. Интегратор уведомлён и подтвердил добавление sequence в своей области DTO; здесь DTO не менялся.
- Все гости в этом pre-MVP однодневные. Finish рассчитывает оставшихся и завершает их присутствие; ночующие гости/многодневные бронирования из полного MVP отложены. Это явно более узкий контракт pre-MVP, а не полная реализация master plan.
- Частичный workProgress живёт в PlayerState; отмена/reset подключения сбрасывает незавершённое действие без расходования ресурсов. Готовые результаты остаются.
- Tick ограничивает один вызов 30 с и считает внутренними шагами ≤0.1 с; долгий stall не создаёт часы фонового прогресса. Heartbeat не продлевается от самого Tick.
- GUID расходников обеспечивает уникальность; расписание/события не используют случайность. Порядок игровых событий воспроизводим, GUID строк побайтово не детерминирован.
- При досрочном Finish гости завершаются сразу; обычные вход/выход используют физические маршруты. Удерживаемый чемодан выезжающего гостя снимается с рук, чтобы его нельзя было продублировать/унести в следующий день.

1. `dotnet build Compile.csproj --no-restore --nologo` в отдельном временном каталоге, .NET 9; прямые ссылки на Unity 6000.3.2f1 UnityEngine.CoreModule.dll и UnityEngine.JSONSerializeModule.dll. **0 ошибок, 0 предупреждений.** Проект компилирует неизменённый HotelTypes.cs, два runtime файла и тесты.
2. `dotnet run --project Run.csproj --no-restore`: **19/19 тестов прошли**. Используются настоящие Unity Vector3/Mathf из установленного CoreModule. Только native JsonUtility заменён во временном harness на System.Text.Json (IncludeFields=true, IgnoreReadOnlyProperties=true), поскольку нативный serializer требует запуска Unity. Файловые операции/backup/checksum выполнялись реально в отдельных temp-каталогах.
3. `git diff --check` — без замечаний.

Набор RunAll покрывает начальный мир/подготовку, дистанцию/стены/права/NaN, двух игроков и disconnect, конечные запасы, бельё/мусор/утилизацию, work lease/дублирование, независимые repair/mop, гонку заселения и маршруты через двери с обходом стойки, доставку и неверный номер, локальные жалобы и компенсацию, однократную оплату, тележку, покупки, долг/пополнение/границу дня, unattended recovery, save roundtrip/held release, corruption/backup/checksum, future schema/невалидные данные, продолжение маршрута после load, два полных дня с обновлением/сохранением/загрузкой.
